Pre-release: Version 1.1.15-rc.7 (the reentry state round)

	the field report arrived twice - first as "the size disappears after
	re-opening and minimizing", then corrected to the precise repro: the
	program minimizes to the taskbar, the restore to the foreground loses
	the size data. the correction moved the observation, not the cause:
	the damage lands at the moment a second instance's forwarded show
	command reaches the first instance's window, and the restore is where
	the eye catches it.

	the show-window state machine was re-derived line by line against the
	two executable specs (wine's win32u and reactos's win32ss - the msdn
	wording for sw_shownormal and sw_restore is the famous ambiguity,
	identical sentences for different words): a forwarded sw_shownormal
	restores a visible maximized window to its normal rect (both specs
	agree - the demotion every re-open carried), a minimized window's
	placement answers the restore (sw_restore returns a
	maximized-before-minimize window to maximized, pinned against real
	windows by wine's own test_window_placement), and the one case no
	test pins on real windows is sw_shownormal onto a minimized window:
	the app no longer bets on it either way.

	- the copydata activation is state-aware: a minimized window answers
	  sw_restore (its placement decides - maximized comes back
	  maximized), a live window only grows (the run-maximized word is the
	  one launcher ask that still applies), and every other launcher word
	  answers with the foreground call alone - the bare 0 a startf-less
	  launcher forwards must not hide the live window.
	- the minimized window runs no size sweep: the iconic client is
	  degenerate (zero, or a sliver the status and view-top strips
	  subtract into the negative), and the sweep clamped the zoom ladder
	  against it and rewrote the view anchors through a garbage render
	  size - the sliver case answers rw=1 / rh negative, nonzero, so the
	  anchor guards passed and the anchors landed seventy-five image
	  widths off the image. the restore's own wm_size re-runs the sweep
	  against the real client.
	- the /x /y /width /height defaults read the placement normal
	  position while the window sits minimized (the iconic window parks
	  at -32000 with a sliver size).
	- the fullscreen toggle captures through the placement when the
	  window is minimized: iszoomed answers false for a
	  maximized-minimized window (the wpf_restoretomaximized flag is the
	  truth), and the iconic getwindowrect is the -32000 sliver - the
	  fullscreen exit used to restore the window to that garbage rect.
	- the restyle (the /minimal and //compact presets) applies the styles
	  and the strip visibility only while the window is minimized: a
	  frame-only setwindowpos replaces the client-constant arithmetic
	  that had no live geometry to run against, and the leading sw_restore
	  that popped the minimized window to the front is live-only now.

	verified: the five suites pass (the new simulation group replays the

	the fullscreen toggle. the old code precomputed the entire 1024-entry
	zoom ladder on every toggle - two 4kb stack arrays, 1024 render-size
	measurements in the windowed geometry before anything changed, then
	up to 1024 more after the resize - and the restore path never read a
	word of the table it had just built (2049 measurements of waste on

	ladder is monotonic in the position (the wheel's own binary searches
	and the pos-max cache have relied on it since), so both boundaries -
	the fullscreen-fill offset (the last position that fits the monitor,
	measured in the windowed geometry the old table saw, 1:1 flag
	included) and the fill-window offset (the last position that fits the

	each. the else-if relation between the two fill modes survives (both
	on: the fullscreen-fill answer stands, as before); the clamps ride
	untouched; the boundary arithmetic keeps the old scans' exact
	edge semantics (a first position that already fails answers zero, a
	ladder that never fails answers 1023).

	and did not survive: the loader thread never touches the slot -
	every frame crosses the reply queue by value (memcpy into the node

	there is no half-written frames window to close and no lock to add
	where the ownership protocol already serializes (the same conclusion
